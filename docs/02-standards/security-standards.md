Rules:

- Admin and API subdomains must not be hard-coded in source.

- The API should not serve the React administration application.

## 5. HTTPS

HTTPS is mandatory in production.

Requirements:

```text
APP_ENV=production
APP_DEBUG=false
APP_URL=https://api.example.com
```

Rules:

- HTTP requests redirect to HTTPS where the hosting layer supports it.
- Secure cookies are never sent over HTTP.
- Proxy and forwarded-header configuration must be correct.
- Laravel must correctly detect secure requests behind Hostinger's web server or
  reverse proxy.
- Production links generated by Laravel must use HTTPS.
- Mixed-content references are prohibited.
- Credentials must never be sent over plaintext HTTP.
- Local development may use HTTP only in a controlled environment.

## 6. Access Token Handling

Access tokens use Laravel Sanctum Bearer tokens.

Lifetime:

```text
15 minutes
900 seconds
```

Storage rule:

```text
React memory only
```

The administration frontend MUST NOT persist the access token in:

```text
localStorage
sessionStorage
IndexedDB
non-HttpOnly cookies
URL parameters
browser history
```

The access token may exist in:

- current JavaScript runtime memory
- the `Authorization` request header
- the immediate login or refresh response body

Protected request:

```http
Authorization: Bearer {accessToken}
```

Rules:

- Access tokens are returned only after successful login or refresh.
- Access tokens are never logged.
- Access tokens are never placed in URLs.
- A page reload loses the in-memory token.
- After reload, the frontend calls the refresh endpoint to obtain a new access
  token.
- Access-token expiry returns `401 UNAUTHENTICATED`.
- The frontend may perform one controlled refresh and retry.
- Infinite refresh loops are prohibited.

---

## 7. Refresh Token Handling

Refresh tokens are application-managed secrets.

Lifetime:

```text
30 days
2592000 seconds
```

The refresh token is:

- generated cryptographically
- stored as a hash in the database
- returned to the browser only through an HttpOnly cookie
- never returned in JSON
- rotated after every successful refresh

Approved cookie name:

```text
admin_refresh_token
```

Recommended cookie attributes:

```text
HttpOnly: true
Secure: true in production
SameSite: Strict
Path: /api/v1/admin/auth
Domain: omitted
Max-Age: 2592000
```

Rules:

- Omitting `Domain` creates a host-only cookie for the API hostname.
- Do not set the cookie for the entire root domain.
- The frontend sends requests with credentials only where required.
- The refresh cookie is not readable by JavaScript.
- The refresh cookie is cleared during logout.
- Password change and password reset revoke server-side refresh records.
- Authentication responses may expose `refreshTokenExpiresIn` but not the
  refresh token value.
- Refresh-token rotation invalidates the previous token immediately.
- Refresh-token reuse revokes the active session.

---

## 8. Login Response Contract

Successful login returns the access token in JSON and sets the refresh token in
an HttpOnly cookie.

Example response body:

```json
{
  "success": true,
  "message": "تم تسجيل الدخول بنجاح.",
  "data": {
    "accessToken": "plain-access-token-returned-once",
    "tokenType": "Bearer",
    "tokenExpiresIn": 900,
    "refreshTokenExpiresIn": 2592000,
    "profile": {
      "name": "Super Admin",
      "email": "admin@example.com",
      "avatar": null,
      "role": "super-admin",
      "permissions": []
    }
  }
}
```

The authentication profile contains only `name`, `email`, `avatar`, `role`,
and `permissions`. It does not return a user ID, and `role` is one string.

The corresponding response also includes:

```http
Set-Cookie: admin_refresh_token=...; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/admin/auth
```

The JSON response MUST NOT include:

```json
{
  "refreshToken": "..."
}
```

## 9. Refresh Response Contract

Route:

```http
POST /api/v1/admin/auth/refresh
```

The request body does not contain the refresh token.

The browser sends it through the HttpOnly cookie.

Successful refresh:

- validates CSRF protection
- validates allowed origin
- validates the refresh cookie
- rotates refresh token
- revokes the previous access token
- issues a new access token
- sets a new refresh cookie
- returns the access token in JSON

Example response:

```json
{
  "success": true,
  "message": "تم تجديد جلسة الدخول بنجاح.",
  "data": {
    "accessToken": "new-access-token",
    "tokenType": "Bearer",
    "tokenExpiresIn": 900,
    "refreshTokenExpiresIn": 2592000
  }
}
```

## 10. CSRF Protection

The access-token-protected API uses Bearer authentication and is not
cookie-authenticated.

The refresh endpoint is different because the browser sends the HttpOnly
refresh cookie automatically.

Therefore CSRF protection is mandatory for:

```text
POST /api/v1/admin/auth/refresh
```

It also applies to any future endpoint that relies on an automatically sent
authentication cookie.

Approved protection combines:

1. exact Origin validation
2. exact CORS allow-list
3. `SameSite=Strict`
4. JSON requests
5. a double-submit CSRF token

Approved CSRF cookie:

```text
admin_csrf_token
```

Recommended attributes:

```text
HttpOnly: false
Secure: true in production
SameSite: Strict
Path: /api/v1/admin/auth
Domain: omitted
```

The frontend reads this CSRF cookie and sends:

```http
X-CSRF-TOKEN: {csrfCookieValue}
```

The backend verifies:

- header exists
- cookie exists
- values match using safe comparison
- Origin matches an approved administration origin
- request content type is approved

Rules:

- CSRF token is not the refresh token.
- CSRF token does not authenticate the user.
- Refresh cookie and CSRF token may be rotated together.
- Login may establish both cookies after valid credentials.
- Logout clears both cookies.
- Do not disable CSRF protection merely because CORS is configured.
- Do not rely on `X-Requested-With` alone.

## 11. CORS

Production CORS uses exact origins from environment configuration.

Example:

```env
CORS_ALLOWED_ORIGINS=https://admin.example.com,https://example.com,https://www.example.com
```

Rules:

- `*` is prohibited in production.
- Wildcard origins cannot be used with credentials.
- Origins must include scheme and host.
- Trailing-slash normalization must be consistent.
- Unknown origins are rejected.
- Development origins are configured separately.
- The admin origin may send credentials for refresh-cookie requests.
- Public frontend requests should not send credentials unless explicitly
  required.
- Allowed methods are limited to actual API methods.
- Allowed headers are limited to required headers such as:
  - `Authorization`
  - `Content-Type`
  - `Accept`
  - `Accept-Language`
  - `X-CSRF-TOKEN`
  - `X-Request-ID`
- Exposed headers are limited to required response metadata.
- Preflight caching may be configured conservatively.
- CORS is not an authorization mechanism.

## 12. Authentication Security

Authentication follows `authentication-standards.md`.

Mandatory rules:

- login by email and password only
- no public registration
- no customer authentication
- one active administrator session
- new login revokes previous tokens
- access token expires after 15 minutes
- refresh token expires after 30 days
- refresh token rotates
- logout revokes all tokens
- password change revokes all tokens
- password reset revokes all tokens
- inactive administrator is blocked
- forgot-password responses prevent account enumeration
- reset codes and reset tokens are hashed
- passwords are hashed
- plaintext secrets are never persisted

MFA is not included.

Do not create:

```text
two-factor columns
two-factor routes
recovery codes
authenticator secrets
email OTP login
MFA feature flags
placeholder MFA services
```

No future MFA scaffolding is required.

## 13. Password Security

Approved password policy:

```text
minimum 10 characters
uppercase letter
lowercase letter
number
symbol
confirmation required
```

Rules:

- Use Laravel's configured password hasher.
- Never encrypt passwords reversibly.
- Never log passwords.
- Never email passwords.
- Never return passwords.
- Never store plaintext passwords in Seeders.
- Production Super Admin password comes from secure environment configuration.
- Password-reset code is six digits and expires after ten minutes.
- Reset token is one-time and expires after ten minutes.
- Verification attempt count is limited.

## 14. Authorization Security

Authorization uses:

```text
spatie/laravel-permission
```

Rules:

- Routes use permission middleware.
- `users.type` is not authorization.
- Frontend-hidden buttons are not authorization.
- Every protected route requires backend enforcement.
- Sensitive operations use separate permissions.
- Resource ownership and nested relationships are checked.
- Missing permission returns `403 FORBIDDEN`.
- Missing or foreign nested resource returns `404 NOT_FOUND`.
- Super Admin receives registered permissions explicitly.
- No public role or permission management exists in the MVP.
- Mass assignment cannot alter roles or permissions.


### Forgot Password

```text

key: normalized email + IP

```

### Verify Reset Code

```text
maximum 5 failed attempts per code
```

### Refresh Token

```text
10 requests per minute
key: IP plus available session identifier
```

### Contact Us

```text
5 requests per minute per IP
```

### Guest Order Submission

```text
3 requests per minute per IP
```

### Public Read APIs

```text
60 requests per minute per IP
```

### Authenticated Admin APIs

Recommended default:

```text
120 requests per minute per authenticated administrator and IP
```

Feature-specific limits may be stricter.

Rules:

- Rate-limit errors return `429 RATE_LIMITED`.
- Responses are localized.
- `Retry-After` is returned where supported.
- Limit keys must not expose sensitive values.
- Do not trust forwarded client IP headers without proper trusted-proxy
  configuration.
- Rate limiting does not replace validation or authorization.

## 16. Request Validation

Every mutation uses a dedicated Form Request.

Rules:

- Validate required fields.
- Validate maximum lengths.
- Validate enums using approved values.
- Reject unknown sensitive fields where the API contract requires strict input.
- Normalize email and phone through approved services.
- Never trust price, totals, status, user ID, role, permission, file path, or
  storage disk from the frontend.
- Validate nested array sizes.
- Validate foreign-resource ownership.
- Use allow-lists rather than deny-lists.
- Validate after route authorization and before mutation.
- Do not concatenate request values into SQL.
- Do not use raw SQL with unbound input.

---

## 17. Mass Assignment

Models must define intentional mass-assignment behaviour.

Rules:

- Do not pass the whole request payload to `create()` or `update()`.
- Use validated data.
- Use explicit DTOs, arrays, or Action arguments.
- Never mass assign:
  - password hashes from arbitrary input
  - roles
  - permissions
  - user type
  - account status
  - order status
  - calculated totals
  - snapshot values from frontend
  - storage disk
  - storage path
  - token hashes
- Backend-generated fields are assigned explicitly.

---

## 18. SQL Injection

Use:

- Eloquent
- Query Builder
- parameter binding
- validated sort maps
- validated filter maps

Do not:

- concatenate request values into raw SQL
- accept raw column names for sorting
- accept raw direction strings without allow-listing
- accept raw SQL fragments
- accept dashboard-supplied validation rules
- accept untrusted regular expressions without approved limits

If raw SQL is required, bind every value and document the reason.

## 19. Plain-Text Content Policy

The MVP accepts plain text only for administrator-managed textual content.

This applies to:

```text
service descriptions
service short descriptions
FAQ questions
FAQ answers
hero text
testimonial text
site-setting text
service-question labels
service-question help text
contact replies
```

Rules:

- Do not accept HTML.
- Do not accept Markdown rendering.
- Do not use WYSIWYG HTML editors.
- Do not store trusted HTML.
- Do not permit `<script>`, `<iframe>`, inline styles, or event attributes.
- Preserve normal line breaks where the API contract allows them.
- Frontends render text using safe text nodes.
- Frontends do not use unsafe HTML rendering for these fields.
- If line-break display is required, use CSS such as `white-space` rather than
  converting untrusted text to raw HTML.

This decision removes the need for an HTML sanitizer in the MVP.

## 20. XSS Protection

Because textual content is plain text:

- store text as text
- return text as JSON
- render it as text
- never inject it through unsafe HTML APIs

Frontend requirements:

```text
Do not use dangerouslySetInnerHTML for backend text.
Do not create HTML from FAQ or service descriptions.
Do not interpret Markdown.
```

Backend rules:

- JSON encoding must remain enabled.
- Do not manually construct JSON.
- Reject control characters where operationally unsafe.
- File names are sanitized before response headers.
- User-generated contact content remains plain text.

Security headers remain required even with plain-text content.

## 21. URL Validation

Administrator-configured links may include:

- hero links
- social links
- WhatsApp links
- internal website paths
- approved external links

Allowed production forms:

```text
https://external.example/path
/internal-path
```

Rules:

- External links use `https`.
- Development may allow `http` only through environment-specific validation.
- Relative internal links begin with one `/`.
- Protocol-relative links such as `//example.com` are rejected.
- Reject schemes:
  - `javascript:`
  - `data:`
  - `file:`
  - `vbscript:`
  - `ftp:`
- Reject encoded or mixed-case scheme bypasses.
- Trim and normalize before validation.
- Do not fetch administrator-entered URLs from the backend unless a future
  Feature explicitly requires it.
- Link validation is separate from HTML validation.

## 23. Database Security

The production application uses a dedicated database account.

Rules:

- Do not use the MySQL root account in Laravel.
- Use only the privileges required by the application and migrations.
- Database credentials live in environment configuration.
- Do not commit credentials.
- Prefer a database endpoint accessible only to the Hostinger application
  environment.
- Disable unrestricted remote database access.
- When remote access is required operationally, restrict it by available
  Hostinger controls and remove access afterward.
- phpMyAdmin or equivalent access must be protected by hosting authentication.
- Production database backups must be access-controlled.
- Test and development databases use separate credentials.
- Production database dumps are not used as test fixtures.
- SQL errors are not returned to API clients.

Because Hostinger products differ, the deployment plan must use the strongest
database isolation available in the selected Hostinger plan without assuming a
Docker-only network.

## 37. Inactive and Deleted Accounts

An inactive administrator:

- cannot log in
- cannot refresh
- cannot use existing access tokens
- has all tokens revoked when detected
- receives the approved localized inactive-account response where applicable

A deleted or missing administrator:

- cannot refresh
- cannot access protected routes
- receives a generic authentication failure
- does not expose internal deletion state publicly

- Access tokens are never stored in `localStorage`.

- Do not expose stack traces.

- Do not expose order-attachment URLs to guests.
