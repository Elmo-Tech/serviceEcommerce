# Service Commerce Backend Constitution

## Core Principles

### I. Documentation Is Authoritative

Repository decisions MUST follow this precedence:

1. this project constitution;
2. `AGENTS.md` for repository workflow, operational safety, and agent
   behaviour;
3. the project overview;
4. backend architecture;
5. shared cross-cutting standards;
6. approved feature-specific business decisions;
7. the active implementation specification generated by Spec Kit;
8. `plan.md`;
9. `tasks.md`; and
10. existing implementation, only when it does not conflict with approved
    artifacts.

A feature-specific business rule MAY specialize a general standard only where
that standard intentionally leaves room for feature-specific configuration. A
feature-specific document MUST NOT weaken, bypass, or contradict this
constitution, backend architecture, or the shared security, authentication,
authorization, API, database, localization, file-storage, testing, and code
standards.

Feature-level overrides MUST NOT return refresh tokens in JSON; weaken HTTPS,
CSRF, CORS, or cookie requirements; remove required permission enforcement;
replace MySQL integrity constraints with frontend validation; change the
approved API envelope; expose raw storage paths; disable required tests;
introduce unsupported queues, Cron jobs, Redis, workers, schedulers, or other
infrastructure; or change localization defaults without first amending the
governing standards.

When a feature genuinely requires an exception to a shared standard:

1. planning and implementation MUST stop;
2. the conflict MUST be reported;
3. the exception MUST receive explicit user approval;
4. the affected shared standard MUST be amended first;
5. this constitution's version MUST be updated when governance meaning
   changes; and
6. dependent documentation MUST be synchronized before planning or
   implementation resumes.

A general repository workflow rule in `AGENTS.md` MUST NOT silently replace a
specific approved feature business decision. Feature business decisions remain
subject to every higher-level cross-cutting safety, architecture, security,
API, database, localization, file-storage, authorization, testing, and code
constraint. Every implemented behaviour MUST be traceable to an approved
requirement, standard, plan item, task, or explicit defect fix. Changes MUST
remain within the requested feature and MUST NOT alter unrelated behaviour.

### II. API-First Backend

This repository MUST remain a Laravel 13 backend-only, API-first, conventional
monolith backed by MySQL. The React administration application and Next.js
public website are external consumers and MUST NOT be implemented or rendered
here. Product APIs MUST be versioned under `/api/v1`; administration APIs MUST
be under `/api/v1/admin`, and administrator authentication MUST use
`/api/v1/admin/auth/*`. Laravel MUST NOT gain
Blade-based product interfaces unless an approved feature requires a
backend-owned email template or rendered document. Approved routes, payload
keys, response shapes, HTTP semantics, error codes, pagination, and
authentication contracts are compatibility commitments. API keys use
`camelCase`; database columns use `snake_case`.

### III. Simple Architecture With Clear Boundaries

The implementation MUST use the simplest Laravel structure that preserves
correctness: thin Controllers, dedicated Form Requests for mutations, API
Resources for serialization, Actions for multi-step workflows, focused
Services for reusable domain or infrastructure behaviour, Query classes for
complex reads, Policies and permission middleware for authorization, and
direct Eloquent CRUD for genuinely simple operations. Complex workflows and
reusable business rules MUST NOT live in Controllers. Business-critical
mutations MUST have explicit transaction boundaries. An Action, Service,
Repository, Interface, DTO, Event, Listener, Job, or other abstraction MUST NOT
be added without a current requirement. Generic repositories, speculative
layers, placeholder functionality, unused schema, and future scaffolding are
prohibited.

### IV. Database Integrity Is Mandatory

MySQL is authoritative for persisted state. True invariants MUST use
appropriate foreign keys, unique constraints, indexes, transactions, and row
locks or atomic operations when concurrency can violate them. Application
validation MUST NOT be treated as the final uniqueness or integrity control.
Business states MUST use backed PHP enums over scalar columns, never native
MySQL `ENUM`; money MUST use precise storage, never floating point. Historical
orders MUST preserve approved immutable snapshots and MUST NOT depend only on
mutable customer, address, catalogue, option, question, or pricing relations.
Tests MUST use a dedicated MySQL database and MUST NOT use production data.

### V. Authentication and Session Security

Administrator authentication MUST use Laravel Sanctum Bearer access tokens with
a 15-minute lifetime and custom rotating refresh tokens with a 30-day lifetime.
The access token MUST be returned in JSON, and the React client MUST keep it in
memory only. Refresh tokens MUST be hashed at rest, transported only through an
HttpOnly, Secure, host-only cookie, never returned in JSON, and protected by
CSRF and exact allowed-origin checks.
Only one administrator session may be active; login, refresh, logout, password
change, and password reset MUST apply the approved rotation or revocation rules.
Inactive administrators MUST NOT authenticate, refresh, or use existing access
tokens. Plain passwords, access tokens, refresh tokens, reset tokens, and
recovery codes MUST NOT be persisted or logged. Tokens MUST NOT appear in URLs,
`localStorage`, or `sessionStorage`. Administrator registration, MFA, Remember
Me, device management, session-management UI, and future MFA scaffolding are
outside the MVP.

### VI. Explicit Authorization

`spatie/laravel-permission` MUST be the authoritative roles and permissions
mechanism. Every protected administration operation MUST enforce the explicit
backend permission defined by its feature, plus resource ownership and workflow
rules where applicable. The `super-admin` role MUST receive every registered
permission explicitly; `users.type`, frontend visibility, wildcard
permissions, and a hidden primary `Gate::before` bypass MUST NOT grant access.
Materially different operations MUST use distinct permissions. Missing or
invalid authentication returns `401`, missing permission returns `403`, and a
genuinely missing or approved non-disclosed nested resource returns `404`.
Nested resources MUST always be verified against their parent.

### VII. Guest Customer Model

Customers MUST remain unauthenticated guest domain records separate from
administrator `users`. The MVP MUST NOT add customer registration, passwords,
tokens, roles, permissions, dashboards, or order portals. Customer matching
MUST use backend-normalized E.164 phone numbers, with Egypt as the default
country while accepting valid international numbers. Guest submissions MUST
NOT silently overwrite administrator-managed customer identity data. Orders
MUST preserve submitted customer and address details as historical snapshots.
Customer authentication is outside the current approved domain and MUST NOT be
scaffolded.

### VIII. Validation and Trust Boundaries

All client input MUST be treated as untrusted and mutation input MUST use
dedicated Form Requests. The backend MUST derive or control normalization,
slugs where generated, hashes, storage names and paths, prices, totals,
statuses, snapshots, roles, permissions, ownership, actor identity, and
default-address invariants. Frontend-supplied prices, totals, status
transitions, roles, permissions, ownership, normalized identifiers, file
locations, storage disks, and snapshot values MUST NOT be authoritative.
Filters, sorts, includes, URL schemes, enum values, file types, and configurable
validation options MUST use explicit allow-lists. Request values MUST never be
concatenated into SQL.

### IX. Plain-Text Content Safety

Administrator-managed and customer-submitted text MUST be plain text in the
MVP. Trusted HTML and Markdown input or rendering MUST NOT be introduced
without an approved feature and security change. Unsafe HTML rendering is
prohibited. URL validation MUST reject `javascript:`, `data:`, `file:`, and
`vbscript:` schemes. Public external links MUST use HTTPS; internal links MAY
use approved relative paths.

### X. File Security

Uploads MUST use Laravel Filesystem through a configurable approved disk and
cryptographically random server-generated names. Validation MUST cover upload
success, extension, detected MIME type, size, count, and domain context. Raw
storage paths MUST never be returned. Executable files, SVG, HTML uploads, and
archive extraction are prohibited. Guest APIs MUST NOT expose order-attachment
URLs. The approved public-storage limitation MUST remain explicit: possession
of an exact public URL can bypass Laravel authorization. Public storage MUST
NOT be described as private. Antivirus scanning, image optimization,
transcoding, thumbnail generation, and cleanup Jobs MUST NOT be claimed or
introduced unless a later approved feature provides them.

### XI. Localization

The backend MUST support Arabic (`ar`) and English (`en`). Arabic is the default locale and English is the fallback locale.
Locale MUST resolve from `Accept-Language`, including supported base-locale
normalization, before validation and response messages are produced. Responses
MUST return the approved `Content-Language` and `Vary` metadata. User-facing
API messages, validation, and backend-generated email MUST use translation
keys. Routes, JSON keys, database columns, roles, permissions, error codes,
enum values, slugs, and other machine identifiers MUST remain stable English
values. Approved public content MUST preserve required Arabic and English
values. Customer-generated content MUST NOT be auto-translated.

### XII. Stable API Contracts

All JSON endpoints MUST use the shared success and error envelopes in the API
standard, except an approved `204` response or file stream. Success responses
MUST NOT add meaningless fields such as `code: null`. Errors MUST combine
stable English machine codes with localized safe messages and MUST NOT expose
stack traces, SQL, absolute paths, internal exception details, credentials,
hashes, tokens, or raw file paths. Operational lists MUST use bounded
pagination. Search, filtering, sorting, includes, and pagination MUST be
validated and allow-listed. Approved routes and response keys MUST NOT change
for implementation convenience; breaking changes require an approved
compatibility strategy or API version.

### XIII. Testing Is Part of Implementation

Every behaviour change MUST include risk-appropriate automated tests using Pest
and a dedicated MySQL test database with `RefreshDatabase` where appropriate.
API Feature Tests MUST cover relevant success, validation, unauthenticated,
forbidden, nested not-found, business-rule, localization, persistence,
contract, side-effect, and file scenarios. Focused Unit Tests are required only
for isolated logic with clear value. Critical race-sensitive rules MUST use
real MySQL concurrency tests. Approved Laravel fakes MAY isolate storage, mail,
queued work, uploads, and time when they preserve the real boundary being
tested. Tests MUST be deterministic, isolated, order-independent, and free of
`sleep()` and Eloquent mocking in API Feature Tests. A feature is not complete
without its required tests.

### XIV. Code Quality Gates

Completed implementation MUST pass the repository-supported Pest suite,
Laravel Pint, and Larastan/PHPStan. Mandatory failures block completion and
merge. Static-analysis failures MUST NOT be suppressed without an approved,
documented reason. Code MUST follow the pinned PHP version, use strict types
where required, use descriptive English names, and avoid duplicated business
rules. Completed work MUST NOT contain debugging calls, temporary routes,
plaintext secrets, commented-out implementation, or unresolved placeholder
TODOs.

### XV. Security and Production Safety

Production MUST use HTTPS, `APP_ENV=production`, `APP_DEBUG=false`, exact CORS
origins, secure cookie settings, trusted proxy configuration, protected
environment secrets, non-root database credentials, disabled directory
listing, and non-executable upload directories. The target hosting environment
is Hostinger; plans MUST NOT assume Docker, Redis, persistent queue workers,
Cron, scheduler access, or shell-command availability without verified support
and an approved feature need. Authentication recovery email is synchronous
under the current approved standard. Infrastructure, background work, or
delivery guarantees MUST NOT be claimed when they are not implemented and
operationally supported.

### XVI. No Unapproved Scope Expansion

Only the active approved feature may be implemented. Customer authentication,
user or role management, MFA, payments, exports, dashboards, analytics, audit
systems, caches, Redis, workers, third-party integrations, new hierarchy
levels, generic media systems, extra statuses, and extra routes MUST NOT be
added unless an authoritative feature specification explicitly approves them.
A possible future need is not a current requirement. Unrelated refactors,
dependency upgrades, schema, routes, and scaffolding are prohibited.

### XVII. Feature Workflow

Every feature MUST proceed through: approved feature reference, specification,
clarification when material ambiguity exists, plan, tasks, analysis, and
implementation. Before implementation, the responsible agent MUST inspect
applicable standards and existing code, identify affected routes and
migrations, perform the Constitution Check, and report unresolved conflicts.
Planning and implementation MUST stop until every governing-document conflict
is resolved and any approved exception is recorded in the affected governing
files.
The plan and tasks MUST cover traceability, authorization, validation,
localization, API contracts, security, database integrity and concurrency,
tests, quality gates, and documentation. Implementation MUST NOT begin from a
vague request or before required artifacts are complete.

### XVIII. Governance

Every principle in this constitution is mandatory. Each plan MUST include a
Constitution Check before research and after design. An intentional exception
MUST identify the violated rule, justify why compliance is impossible,
document risk and mitigation, and receive explicit user approval before
implementation. Exceptions MUST NOT silently weaken a principle or approved
business rule.

## Project-Wide Constraints

Detailed endpoint contracts, schemas, validation limits, permission names,
status transitions, MIME lists, and feature acceptance criteria belong in the
applicable shared standard and feature artifacts, not this constitution. Those
artifacts MAY specialize these principles but MUST NOT weaken or contradict
them. The platform remains a single-business, backend-only Laravel monolith
using one primary MySQL database, Sanctum, Spatie Permission, Spatie Query
Builder, Laravel Filesystem, Pest, and only approved queue use. React, Next.js,
customer portals, persistent backend carts, online payment, multi-tenancy,
microservices, modular-monolith layers, and speculative infrastructure remain
outside the repository unless governance and product documentation are amended
first.

## Feature Delivery and Quality Gates

Before implementation, every active feature MUST have an approved, testable
specification, a plan with a passed Constitution Check, and a
dependency-ordered task list that includes mandatory tests and verification.
Each requirement MUST map to acceptance scenarios and implementation tasks.
Plans MUST identify trust boundaries, permissions, data invariants,
transactions and locks, localization, API compatibility, file compensation,
deployment assumptions, and test strategy where relevant. Completion requires
the intended code and documentation changes, passing supported automated
checks, an inspected final diff, no unrelated modifications, and explicit
reporting of any command that could not run.

## Amendment and Versioning Procedure

This constitution supersedes other repository practices. Amendments require:

1. a stated reason and compatibility impact;
2. identification of affected principles, standards, templates, features, and
   implementation;
3. synchronized dependent documentation before implementation;
4. semantic versioning and an ISO-formatted amendment date; and
5. a Sync Impact Report preserved at the top of this file.

Version changes follow semantic versioning: MAJOR removes or incompatibly
redefines governance; MINOR adds a principle or materially expands mandatory
behaviour; PATCH clarifies wording without changing required behaviour. Every
plan and review MUST verify compliance. Reviewers MUST reject undocumented
exceptions, missing traceability, failed mandatory gates, or unresolved
authoritative conflicts.
